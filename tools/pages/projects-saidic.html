Saidic gives a business a chat widget for its website. Visitors chat with an assistant that answers from the business's own information and can carry out actions against the business's systems: look up an order, cancel a subscription, check stock. Staff follow and join conversations from a dashboard. A research agent builds a public directory of companies, and campaigns send outreach e-mail to companies chosen from it.

How an answer is made

Everything a business gives the assistant (its profile, questions and answers, About text, files, verified websites, documents pushed by its own programs through an API key) becomes sources, documents and passages. Passages are embedded into pgvector; directory search is Postgres full-text search. When a visitor asks something, the message is routed, the passages that answer it are retrieved and judged, a reply is generated, and the reply is checked against the passages it claims to rest on.

Every turn is recorded: what the assistant took the message to be, what it read, its checks, the time it took and what it cost. The dashboard's Trace page shows that record, and the questions that could not be answered are kept as a list, because those are the gaps in the knowledge the business should fill.

Actions

An action is an API endpoint the business configures: a URL, a method, the parameters to collect from the visitor, and a credential. The assistant works out which parameters are missing, asks for them in plain language, validates them against the business's patterns, then calls the endpoint and explains the result.

Credentials are the dangerous part, so they are treated that way. Secrets are encrypted at rest with AES-256-GCM under a key from the environment, with key rotation; the API never returns a secret, only a fixed mask, and sending the mask back leaves the stored value unchanged. Token-based credentials (login exchange, OAuth client credentials, OAuth password grant) are refreshed by an hourly job before they expire, with simultaneous executions sharing one acquisition through a database lock, and a daily job checks each credential's health.

Every outbound call to a URL a business supplied goes through one gate: http and https only, no internal network address by literal or after name resolution, on every redirect hop, with a timeout and a response size limit. The connection is made to the address that was checked, so a DNS answer that changes between the check and the connection cannot redirect the call inward. The crawler's browser reaches the network through a local checking proxy for the same reason. Patterns a business writes are matched with a linear-time engine, never the backtracking one.

Realtime

Two WebSockets: the visitor's chat and the staff's live chat. Redis pub/sub fans messages out across API instances, and holds the short-lived state (rate limits, presence, buffered heartbeats). A socket's token travels as a subprotocol, never in the query string, because Nginx's error log prints a failing request's whole address and cannot be told otherwise. The access log uses a format with no query strings at all. Those two decisions came from reading what the logs would contain, not from a checklist.

The consolidation

Saidic did not start this way. It was a Django REST backend with Celery and Celery beat, a Go service for WebSockets and tracking, a FastAPI "Logic Engine" for the chat agent with its own Celery, a Research Engine with its own API, two Redis instances, Elasticsearch, and an in-memory FAISS index. It worked, and it was seven things to deploy, monitor and keep in step.

The rule of the consolidation was that behaviour stays identical: the same paths, request and response shapes and status codes, so the two front ends did not have to change. A small compatibility layer reproduces Django REST Framework's field validation, error messages and page-number pagination down to the wording, and every deliberate difference is recorded with its reason. Elasticsearch and FAISS are gone: directory search is Postgres full-text search and similarity is pgvector.

Inside the backend, each module has a models.py, a service.py and a router.py, and the boundaries are enforced by a script that runs with the tests: a module imports another only through its service, agents contain no SQL, and the core and AI layers import nothing from above them. The whole thing runs as one image in three roles (API, general worker, crawler worker) behind Nginx, with Compose files for development and production.

Where it stands

The backend, its tests and the local stack exist and run, and the demo can be put on Cloudflare quick tunnels to try from a phone. The cutover of the development database to the new backend has not been carried out, and production deployment is a later phase. The technical docs end with a section called "What is not verified", and I would rather the page said that than implied otherwise.
